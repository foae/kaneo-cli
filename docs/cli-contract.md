# CLI contract

This is the binding contract for the command surface. Help, version, profile management, authentication, JSON API operations, file transfers and browser URL handoffs are implemented; [verification](verification.md) distinguishes real acceptance from fixture coverage and records API discrepancies.

## Names and input

`kaneo-cli <group> <verb[-object]>`: `instance get-status`, `auth get-session`, `org accept-invitation`, `project list`, `task update-status`. Omit the object when the group already identifies it. Use `profile` for local configuration; do not collide with the server's `config` operations. The reviewed machine-readable inventory is authoritative for individual mappings; aliases are not additional coverage.

Use `--profile NAME`, `--api-url URL`, `--timeout DURATION` and `--yes` consistently. `URL` is the full API base URL, normally including `/api`; it is not a dashboard URL. The CLI never appends `/api`, probes alternate endpoints, or retries against another destination. It validates and normalizes ordinary spelling (surrounding whitespace, scheme/host case, default ports, and one trailing slash) while preserving the base path. API requests may follow same-origin redirects, but reject cross-origin redirects even without credentials. Explicitly configured HTTP is allowed for self-hosted instances, with a stderr warning before transmitting credentials; never downgrade HTTPS automatically. Validate malformed URLs before network access.

## Profiles and effective destinations

The selected profile resolves from `--profile`, then nonempty inherited `KANEO_PROFILE`, then the persisted default selection. API URL and timeout resolve independently from flags, then nonempty inherited `KANEO_API_URL`/`KANEO_TIMEOUT`, then that profile, then their documented defaults. Empty or uninherited environment variables are unset. The defaults are `default`, `https://cloud.kaneo.app/api`, and 30s.

`profile get [NAME]` is an offline effective-settings view: it prints the canonical effective API URL and timeout, their sources, and credential backend metadata only for the effective URL. It makes no server request or keyring access. A positional `NAME` selects that profile before `--profile` or environment profile selection, records `sources.profile` as `argument`, and still permits flags and environment settings to override its stored values. A new implicit default can be viewed without persisted configuration; an explicitly requested missing profile fails. `profile list` and `profile set` remain stored-settings views, and `default` always means the persisted default selection rather than effective resolution.

Local profile management and logout resolve profile selection without parsing request URL or timeout overrides. `profile set` validates the explicit settings it persists; `profile get` still validates the effective request configuration. Logout removes all recorded credential bindings for its selected profile.

When an API client is constructed with only the implicit Cloud default, emit one stderr warning per invocation before its first request. Emit the same warning before API-key login persists a credential to that default. Do not warn for an explicit Cloud URL, profile inspection, help, version, or navigation-only browser handoffs. After login persists a destination, profile-backed use is no longer an implicit default.

Security warnings persist across invocations: unencrypted credential storage warns once per profile/API URL (reset on keyring restoration or credential deletion); credential-bearing HTTP warns once per profile/origin. Existing fallback credentials warn on their first use after upgrading. Failed warning persistence must not suppress the warning or fail an otherwise valid API operation.

For a JSON operation that receives invalid JSON, diagnostics may safely explain that HTML can be a dashboard or proxy response, that API bases normally include `/api`, and that `profile get` shows effective settings. Never include response bodies, credentials, or redirect URLs in that hint; preserve existing error and exit-code behavior. Binary downloads are not JSON operations.

Document operation-specific named flags for scalar path/query parameters. Body-bearing mutation help includes a generated static JSON field reference from the pinned OpenAPI schema: required and optional fields, types, enums, descriptions, and nested object or array requirements. It never parses a schema or adds validation at runtime. Complex bodies accept `--body-file PATH` or `--body-file -` for stdin, are validated before any network access and are passed through unchanged so unknown schema-permitted fields and numeric precision survive. Two file operations construct their request from a local file instead: `task create-image-upload` requests a presigned URL, streams the bytes to storage with a client that never carries the API credential, and prints only `{"key":"..."}` for the finalize operation; the presigned URL and transfer headers are never printed. `user upload-avatar` sends a bounded base64 body. A flag is present only when explicitly supplied: omitted, JSON null, false, zero and empty string are distinct. `workspace` help directs operators to `org list` for workspace IDs, and every label `--id` flag is labeled `Label ID`. A few operations additionally carry a short hand-written note after the generated reference, recorded as a supplement in `api/provenance.json` because the pinned spec does not document the behavior at all: the reserved `planned` and `archived` task statuses accepted by `task update-status` and `task create`, their rejection by `task move`, and the silent status coercion performed by `task import`.

No implicit prompts, even on a TTY. Device login is an explicit interactive action; describe its behavior on a non-TTY and provide a no-browser path. Destructive actions (deletes, revocations, removals, resets and equivalent irreversible state changes) require `--yes` before making any request, independent of terminal type. This includes local credential removal via `auth logout` and `profile delete`. Bulk mutation must report partial failure rather than successful exit for incomplete work. The same holds for documented continuation protocols: when `label delete` or `github import-issues` answers HTTP 202 (or the import reports `pending: true`), the complete response is written to stdout and the command exits 5 with error code `incomplete`. The CLI never repeats the request itself; the caller repeats the same deletion, or repeats the import with the returned `runId` in the body, until it completes.

## Output

- Successful JSON: API response directly on stdout, no envelope; emit a trailing newline. JSON null remains `null`. The task-image upload intentionally emits only the safe object key, as described above.
- Secret-read exceptions: `oauth get-id-token` replaces a non-null `idToken` with `"[REDACTED]"`; `gitea get-integration` does the same for `webhookSecret`; `auth get-session` does the same for the nested `session.token`, which carries the credential itself and on the API-key path is the raw long-lived key, while `session.id`, `session.userId` and every `user` field are left unchanged. Missing fields and null values remain unchanged, as do unrelated JSON values, at both the top level and inside `session`: an absent or null `session`, or an absent or null `session.token`, leaves the body unredacted, and a `null` body still prints as `null`. A `session` value that is present but is not a JSON object is rejected rather than printed, because it could itself be the secret. These responses are validated before any output; their whitespace and object-key order may change.
- No-content responses: empty stdout, not `{}` or `null`.
- Ordinary and batch JSON responses are limited to 8 MiB before any stdout output. Oversized responses fail with a local error; binary downloads remain streamed rather than subject to this JSON limit.
- Preserve API pagination shape. No invented `--all` behavior or automatic aggregation; follow actual documented pagination parameters and links.
- Binary downloads: require an explicit destination. Never corrupt stdout with binary bytes by default; refuse overwriting an existing file without an explicit overwrite choice.
- Browser URL handoffs: `auth get-device-authorization-page` prints the initial `/auth/device` URL with `ui=1`; `mcp start-authorization` prints the initial `/mcp/authorize` URL with validated authorization parameters. Both write guidance to stderr and make no HTTP request, load no credential and launch no browser. Exit zero means the URL was written, not authorization completed. Neither follows nor prints secret-bearing redirect destinations.
- Diagnostics and one structured error object go to stderr: `{"error":{"code":"invalid_arguments","message":"..."}}`. The foundation uses `unknown_command`, `invalid_arguments` and `process_failure`; add stable API error codes plus safe HTTP status or operation ID when relevant, never raw credentials/server dumps.
- A failed response's own diagnostic is preserved when the server supplies one: the documented JSON error fields first, and otherwise a `text/plain` body, which the pinned spec declares for most documented 400 and 403 responses and which carries the server's actual explanation. Such a body is whitespace-collapsed and truncated to the existing message limit, and is rejected outright when it is not valid UTF-8 or contains control characters. It is never used for an operation whose request body carries a credential, because a server may echo a submitted value back in its error, and never for a body that parses as JSON: such a body was already offered to the documented-field extraction, so an unrecognized JSON shape stays unechoed, and Go's content sniffing labels an unlabeled JSON body `text/plain`, which means the media type alone cannot establish that the server declared plain text. This stays narrower than echoing a raw body: JSON of an unrecognized shape, HTML, unknown media types and binary payloads still produce only the generic status message.
- `version` and `--version` return the same JSON object with `version`, `commit`, `date`. Help remains human-readable.
- Help output (including root invocation without arguments and subcommand help) and version output perform a best-effort update check for stable release builds against `https://api.github.com/repos/foae/kaneo-cli/releases/latest`. A newer stable version produces one plain-text stderr line: `Update available: kaneo-cli <current> -> <latest>; upgrade: https://github.com/foae/kaneo-cli/releases/latest`. Numeric version precedence is used, with optional `v` prefixes. Development/prerelease builds skip the check. The separate unauthenticated HTTP client sends no Kaneo credentials, refuses redirects, bounds the response to 64 KiB and uses a one-second timeout with invocation cancellation. Offline, rate-limit and malformed-response failures are silent; stdout and exit status are unaffected. No cache/config is written and ordinary API commands do not check.

For automation, avoid progress bars, ANSI escapes, timestamps, and unsolicited stdout. Future human formatting must be explicit, leaving JSON the default. Preserve the documented CLI output contract throughout 1.x; breaking changes require release notes and a major version bump. Upstream API response shapes remain governed by the pinned API baseline and documented compatibility limitations.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Success |
| 1 | Other/local failure |
| 2 | Usage or input error |
| 3 | Authentication or authorization failure |
| 4 | Transport or timeout failure |
| 5 | Other API failure |
| 130 | Interrupted |

Do not infer failure solely from a nullable successful body: `auth get-session` can validly return null. Map documented protocol errors deliberately. Signal cancellation must stop pending requests and device polling, not merely hide their output.
